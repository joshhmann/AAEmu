## 4. Harness gap — surgical notes for the follow-up implementer

### 4.1 Where the probe is hardcoded
- `AAEmu.IntegrationTests/E2e/Gate/ScalingProbeTests.cs:42` — `foreach (var n in new[] { 10, 20, 30 })`; tier list is not env-driven.

- Boot-validity gate :54-56 asserts `Embodied >= Citizens`, which true dormancy violates by design when no humans are present (see §5 anomaly 1).

### 4.2 Why dormant registration (~100 DB rows) is impossible from the harness today
`MySqlDormantBotSource.ListSpecs()` (`AAEmu.Game/Core/Managers/Bots/DormantBotRegistry.cs:74-100`) discovers dormant specs as
`characters ⋈ aaemu_login.users` where username LIKE managed-prefix AND `account_type = HeadlessBot`. The ONLY harness-reachable way to mint such rows is the bridge pair:
- `provision` — `BotDriveBridge.HandleProvision` (`AAEmu.Game/Models/Game/Bots/BotDriveBridge.cs:~1490`) → `HeadlessSession.Provision` (embodies);
- `deactivate` — `HandleDeactivate` (:1528) → `CharacterLifecycleService.Deactivate` (despawn + save; row persists → discoverable dormant spec).

That is one synchronous round-trip per bot (×100) and the probe never calls either. Missing: a bulk seed command on the bridge (e.g. `provisionBatch`/`seedDormant N`) or an SQL-side seeder in the test rig that inserts managed accounts + characters + `playerbot_metadata` home rows directly.
Home metadata prerequisite: `PlayerBotMetadataHomeSource` (`DormantBotRegistry.cs:46-58`) requires `HasHome` in `aaemu_game.playerbot_metadata`; specs without home are skipped forever by proximity matching (`PopulationDirector.MaterializeNearbyDormantSpecs`, `continue` on `TryGetHome == false`).

### 4.3 What a materialize trigger would need to call
The e672b9579 entry points exist and work (dematerialize path proven live):
- Engine path: `PopulationDirector.RunProximitySweep` → `MaterializeNearbyDormantSpecs(humans)` (`PopulationDirector.cs:666-708`), gated on `_options.EnableTrueDormancy && _dormantBots != null` and **non-empty humans list**; budget `TrueDormancyMaterializePerSweepMax` (default 3/sweep); radius `ReducedProximityRadiusM` (default 200 m).
- Humans come from `_humanSnapshotProvider` → `DefaultHumanSnapshot` (:744-763): all in-world characters **except registered bots** — embodied probe citizens can never trigger each other. A trigger therefore needs either (a) a real client session on a NON-managed account standing within 200 m of the dormant homes (the integration tests have `BotTcpLink`/`BotNetworkSession` client machinery that could host it), or (b) a direct test seam calling the public `DormantBotRegistry.Materialize(DormantBotSpec)` (:196)/`Dematerialize(Character)` (:238).
- Sweeps only run when armed: `PopulationDirectorProximityBootstrap` arms on `AAEMU_BOT_PROXIMITY_FIDELITY=1` / `"Bots".EnableProximityFidelity`; `EnableTrueDormancy` alone is inert (verified: registry registered in DI at `Program.cs` diff of e672b9579, but never swept without the proximity flag).

## 10. PB-004 FIXED — proximity-materialized bots now step (2026-08-25, later same day)

- Executor: harness-gap workstream agent (`g2-a5-harness`). Main tree develop @ d989f6639 (instrumentation branch
  already merged). Fix + tests uncommitted at measurement time.
- Defect (blocker ledger PB-004): `MaterializeNearbyDormantSpecs` set fidelity Reduced but never re-armed scheduler
  stepping. Root-caused to TWO stacked gaps, both fixed:
  1. **Producer**: materialization never called `Wake()` (the due path's Dormant→Reduced transition calls Wake
     precisely to "re-arm scheduler stepping"). Fix: `PopulationDirector.MaterializeNearbyDormantSpecs` now calls
     `Wake(spec.CharacterId, "true-dormancy-materialize")` after a successful registry materialize — fidelity is
     already Reduced so Wake goes straight to `_scheduler.Wake` + counters, exactly mirroring the due path.
     (`MaterializeNearbyDormantSpecs` private → internal for rig reach; InternalsVisibleTo AAEmu.UnitTests existed.)
  2. **Consumer**: in a dormancy-only boot (no presence demo, no EnableSchedules) NOBODY ever starts the
     PlayerBotScheduler wake-scan loop — only BotPresenceCoordinator / BotAdminService / BotScheduleBootstrap
     start it — so ALL wakes (due-path AND materialization) queued forever (`isRunning:false`,
     eventQueueDepth grew to 10 with totalStepsRun stuck at 0). Fix: the proximity bootstrap
     (`PopulationDirectorProximityBootstrap`, armed ONLY by the already-non-default
     AAEMU_BOT_PROXIMITY_FIDELITY=1 flag) now also calls the idempotent `IPlayerBotScheduler.Start()`.
     Default-OFF neutrality holds: without the proximity flag nothing changes.
  - Seed-fidelity companion (harness): seeded dormant specs now carry the presence coordinator's roam-loop
    schedule descriptor (`seedDormant` records RecordSchedule alongside RecordHome) — real dormant specs
    (dematerialized ex-presence citizens) have schedules; without one a woken bot executes a single step and
    goes quiet again.
- Unit proof (`AAEmu.UnitTests/Game/Core/Managers/Bots/PopulationDirectorTests.cs`, TUnit, class total 29/29 PASS):
  - `MaterializeNearbyDormant_WakesScheduler_StepsResume` — real manager+scheduler rig; after the internal sweep
    call with a human inside ReducedProximityRadiusM: spec dematerialized from registry, fidelity Reduced,
    TotalMaterializations=1, **TotalWakes=1** (THE regression signal), and the materialized bot EXECUTES a step on
    the pumped scheduler (Executor.Starts contains its id).
  - `MaterializeNearbyDormant_SpecWithoutHome_StaysDormant_NoWake` and
    `MaterializeNearbyDormant_HomeBeyondRadius_StaysDormant_NoWake` — no home / out-of-radius specs stay dormant,
    zero materializations, zero wakes.
