## What the pilot is

The M2b pilot is a **repeatability harness**, not a new gameplay system. It
drives REAL quest templates + REAL unit requirements from the canonical
compact.sqlite3 (via `QuestManager.Load()` + `UnitRequirementsGameData.Load()`)
on **ordinary Character records** (no Connection) through **normal gameplay
services**:

- accept → `CharacterQuests.AddQuest` (real gates: level, race, faction,
  completed-quest chains, repeatable/daily re-accept checks)
- progress → the engine's `UnitEvents` surface (the same handlers the world
  interaction pipeline fires: kills, gathers, talks, interactions, cinema,
  express-fire, aggro, zone-kill)
- turn-in → `QuestManager.DoReportEvents` (the exact path the
  `CSCompleteQuestContextPacket` client packet takes)

Composition rule (AAEmu AGENTS.md #9/#10) is enforced structurally: bots hold
zero quest state of their own; every mutation flows through engine surfaces.
No parallel character/inventory/quest implementation, no bot-only quest state,
no direct DB writes, no quest-engine bypass.

## Signal contract (who reports what)

| Signal | Source | What it means | Action |
|---|---|---|---|
| Bot failure | PlayerbotPilotTests | A quest could not be accepted/progressed/completed through real engine paths on a headless bot | INTEGRATION signal: repro trace (quest id + stage + step/status observed) is the finding |
| Census status | quest_next_missing_census + runnability manifests | Structural wiring of templates/components/acts | STRUCTURAL signal: templates are wired, stages are runnable in isolation |
| Bot failure + census green | both | Engine/wiring/data defect the census cannot see (runtime gates, event plumbing, state transitions) | NEW DEFECT: file a regression card with quest id + stage + repro |
| Bot failure + census red | both | Template-level breakage already tracked by the census | Existing defect; the bot adds a runtime repro layer |

**Rule:** bot-observed failures with no census signal are **new defects
(engine/wiring/data), not harness gaps**. The harness is calibrated to real
engine semantics (see "Calibration" below); a red bot test means the engine
failed a real quest, not that the harness is wrong. The harness has no SKIP
path and no defect allowlist — the M2b table's green bar is 100%.

## Calibration (why the stage loop is what it is)

The pilot's stage driver mirrors the scenario driver EXACTLY (calibrated green
on the same manifests, 189/189): fire the stage's events, then ONE
`RunCurrentStep`, then evaluate. The loop must NOT keep advancing until
"rest": the engine's completion path (`GoToNextStep` → `SetCompletedQuestFlag`
→ `DropQuest` → `Quest.Drop`) leaves a completed quest object in
**Step=Drop/Status=Dropped** — the correct terminal state, but only reachable
BY the REWARD stage. Extra advances before evaluation misread the stage
(attempt 1's quest-251 "Drop" failure was this: the bot HAD completed the
quest — flag set, reward granted — but the driver had already run the reward
step before the READY expectation could observe Reward/Completed).

Rig gaps found and fixed (all are ordinary-character state, not bot-only
state):

- **Faction null → NRE** (UnitReqs.cs:199 `unit?.Faction.MotherId`): a real
  character row always carries a faction. `HeadlessSession` now seeds
  Nuian/NuiaAlliance (148), matching the DB default. No engine change.
- **Completed-flag prerequisites** (1959 needs 1958; 5059 needs 4784): real
  gates (`CompleteQuestContext`). The rig pre-completes them through the
  engine's own `SetCompletedQuestFlag` — the same method the completion path
  calls. No bypass.
- **Character fields for jury-line quests** (5059: `JuryPoint >= 1`,
  `CrimeRecord 1..9`, MotherFaction): set as ordinary character fields, the
  same way `Character.Load` would populate them from the character row.

## Quest-cycle mode (empirical re-accept gate)

**Gate question:** does the engine re-accept a completed quest when
REPEATABLE='f' (cat-34 daily board)?

**Answer (code + runtime evidence): NO.**
- `CharacterQuests.AddQuest` refuses completed non-repeatable quests
  (CharacterQuests.cs:107-120, QuestDailyLimit).
- The daily-reset path (`ResetDailyQuests`) only clears QuestDetail
  Daily/DailyGroup/DailyHunt/DailyLivelihood (7/9/10/11). cat-34 quests carry
  `detail_id=6` (Task), so their completed flags are NEVER cleared — re-accept
  is impossible even across days.
- Test evidence: `ReacceptGate_NonRepeatableDaily_Cat34_RefusedEvenAfterDailyReset`
  — 1959 completes, re-accept refused, flag survives a daily reset, re-accept
  still refused.

**Consequence:** quest-cycle mode is limited to the **88 REPEATABLE='t'
quests**; cat-34 (REPEATABLE='f') falls back to character-cycle. Quest-cycle
mode proven on 5059 (Solzreed's only repeatable quest): 10/10 cycles on the
same character.

## Drift detection

Every failure in the pilot carries a repro trace with quest id + stage +
observed step/status and is recorded in the metrics file's "Failures" section.
The run wrapper / next worker files one regression card per structured failure
(the card body's drift-detection requirement). Attempt 1's failures (quest 251
"Drop", 840 leaks, 5059 NRE) were all harness/rig artifacts — fixed in this
run; **no engine defects were surfaced by the pilot at green**.
