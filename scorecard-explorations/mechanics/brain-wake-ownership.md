## 4. ARBITER EVOLUTION (seam analysis, no implementation)

Question: can priority + `CanActivate` evolve toward eligibility + score + commitment + hysteresis without scheduler changes?

Answer: **yes — no scheduler change is needed; the scheduler never sees the arbiter at all.**

1. **Scheduler seam is `IBotStepExecutor.StepAsync` returning `TimeSpan?`.** The scheduler calls `_executor.StepAsync` (:398-405) and schedules on its return (:447-450). The arbiter decorator implements that same seam (`BotGoalArbiterStepExecutor.cs:16-43`). Any arbitration-internal change (scores, commitment, hysteresis, stickiness) is invisible below the seam as long as the decorator still returns the inner step's delay.
2. **Module seam is `CanActivate → BotActivityDecision` + `Activate → BotActivity`.** Scores can ride new optional members or a widened decision record without touching `IBotStepExecutor` or the scheduler: the arbiter loop (`BotGoalArbiter.cs:157-191`) is the only consumer of `CanActivate`, and `BotActivityContext` (`IBotActivityModule.cs:50-60`) is built by the arbiter per wake — adding score/commitment inputs (prior activity, switch cooldown, hysteresis band) means changing arbiter+context+modules only.
3. **Commitment/hysteresis state has a home already.** `_activeActivity` (`BotGoalArbiter.cs:88`) is per-bot single-active memory with `Forget` (:238); switch debouncing, cooldown timestamps, or score smoothing extend that dictionary's value type — still arbiter-private, still no scheduler involvement. The transition log (:215-216) and `Candidates/Rejections` counts (prereq Part 2) already flow into the audit via `StageArbitrationTrace` (:57-74) without scheduler knowledge.
4. **Constraints (no scheduler change ≠ no risk).** (a) `Activate`-on-change-only (:190-217) means commitment logic must live in the *election* (which candidate wins), not in `Activate` frequency — steady-state wakes never call `Activate`. (b) The staged trace is overwritten every wake (:53-55 in decorator doc) so multi-wake commitment deliberation is invisible unless the stamp schema widens (record columns exist: `DecisionGoal/Policy/Candidates/Rejections/Seed`, `ActorAuditRecord` via gap-observe §1.1 — writers verified only for arbiter-stamp + quest scenario paths). (c) Pressure/death/battle denies are per-module (`CanActivate` denies at High/Critical in quest/needs/homestead/fishing) — a scoring evolution must keep fail-closed denies scoring -inf, not merely low. (d) The one-activity-per-wake + at-most-one-of-0a/0b/0c firing discipline (`BotRoamStepExecutor.cs:635-679`) assumes activity names stay mutually exclusive; scores must still resolve to a single winner — the executor reads string prefixes (`needs.*`, `quest.*`, `homestead.*`, `conflict.*`), so new activities must keep the prefix contract or the branch gates change (executor change, still not scheduler).
5. **G3 verdict interaction.** G3 FAIL-BEHAVIOR/DISCOVERY is about what the behaviors do once elected, not about the election math: scoring+commitment without proven wake behavior still fails G3-behavior; discovery claims still require the wake→terminal join (`DecisionCycleId`, prereq Part 3) on a proven wake, else HARNESS-UNKNOWN.

Proposed single future ownership model (no event bus — uses existing primitives only):

- **One `InterruptLeg(reason, owner)` choke point on the navigation/behavior host** (the extracted executor): the only code allowed to call `actor.Stop/PreemptCurrent` for autonomy legs. It (1) preempts via `PreemptCurrent(reason)` (standstill broadcast included, `GameplayActor.cs:514-527`), (2) clears `PendingLeg` + the owning behavior's target reference (closing today's orphan window where `PendingLeg=null` is hand-rolled at ~18 sites and GOAP's `CurrentActorRequest` goes stale), (3) nudges replan (`ActivePlan=null` for GOAP via existing `DropInFlightRequest`; phase reset for farm/hunt/butcher). Queue drain calls the same choke point instead of `actor.Interrupt` directly (pass the interrupted trace id back so the executor clears on next wake — gap-senses §4.4-2).
- **Policy table, not pub/sub**: a static precedence (death > API-takeover > recovery > conflict > work-leg > roam) evaluated inline at the top of `StepAsync` in the existing branch order — no broker, no subscriptions, no new thread. Each branch declares its preempt rights (party/PvP preempt all; needs/quest/homestead preempt hunt/butcher/route but never party/PvP — already the code's discipline :636-684); the choke point enforces it in one `if` chain.
- **Audit**: every preemption keeps today's shape (interrupted request's own `Interrupted` record + reason string; `PreemptCurrent(reason)` already carries it) — no new record schema. Pressure-rise preemption (currently absent) becomes a policy row (preempt travel legs, keep engaged legs), not a new event type.
- What this fixes: orphan `PendingLeg`/`CurrentActorRequest` references, fire-and-forget `_ = actor.Stop()` receipts (gap-senses §3.5-1), GOAP-busy `Rejected` fresh legs after reference-drop replan (gap-senses §3.5-4). What it does NOT change: lifecycle, single-writer rule, engine tails, scheduler cadence, queue backstop clocks.
